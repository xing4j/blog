# 📜 博客写作质量宪章 v1.0

> 适用范围：xing4j 技术博客全系列文章
> 制定时间：2026-05-23
> 定位：10年+ Java 全栈工程师的高质量原创技术博客

---

## 一、文章立意标准

### 1.1 选题原则
- **有价值**：每篇文章必须解决一个明确的技术问题或填补认知空白，杜绝"凑数"内容
- **有深度**：不做官方文档的搬运工，必须包含自己的理解、踩坑经历或生产视角
- **有边界**：每篇文章聚焦一个核心主题，不贪大求全，宁可拆成多篇
- **不重复**：发布前检索已有文章，避免与已发内容高度重叠；如有关联需交叉引用

### 1.2 读者定位
- **目标读者**：有一定基础的 Java 开发者（1~5 年经验）
- **写作视角**：以"老手写给新手看"的方式，用简洁语言解释复杂概念
- **禁止假设**：不假设读者已知晓文章的前置知识，必要时提供前置阅读链接

## 二、结构规范

### 2.1 强制结构（每篇必含）

```
1. 文章头部（Front Matter）
   - 标题、发布日期、所属系列、标签分类、预计阅读时长

2. 导读段落（≤150字）
   - 说明"本文解决什么问题"、"读完你能收获什么"

3. 正文主体
   - 原理剖析（Why & How）
   - 代码示例（可运行）
   - 生产场景（Real World）

4. 踩坑总结（至少 2 条）
   - 格式：❌ 错误做法 → ✅ 正确做法 + 原因

5. 小结（3~5 条 Bullet Point）
   - 一句话归纳每个核心知识点

6. 参考资料
   - 注明引用来源，优先官方文档、源码、权威书籍
```

### 2.2 禁止结构
- ❌ 通篇流水账（没有小标题层次）
- ❌ 正文超过 8000 字未做分篇处理
- ❌ 仅贴代码不解释（代码块必须有前置说明和关键行注释）
- ❌ 结尾无总结直接结束

## 三、内容深度标准

### 3.1 深度分级（每篇注明等级）

| 等级 | 定义 | 适用场景 |
|---|---|---|
| ⭐ 入门 | 概念介绍 + 基础用法 | 系列开篇、新技术介绍 |
| ⭐⭐ 进阶 | 原理剖析 + 常见问题 | 系列主体文章 |
| ⭐⭐⭐ 深度 | 源码级分析 + 生产调优 | 系列核心篇 |

### 3.2 各等级硬性要求

**⭐ 入门篇**
- 必须有完整可运行的 Demo
- 必须有与同类技术的横向对比表格
- 字数：2000~4000 字

**⭐⭐ 进阶篇**
- 必须有原理图（架构图/流程图/时序图至少一种）
- 必须有"为什么这样设计"的分析
- 字数：4000~6000 字

**⭐⭐⭐ 深度篇**
- 必须有关键源码引用（附 GitHub 链接 + 版本号）
- 必须有生产环境真实案例或数据支撑
- 必须有性能对比数据或调优前后的量化效果
- 字数：6000~10000 字

## 四、代码规范

### 4.1 代码块标准
- 必须标注语言类型（` ```java `, ` ```yaml `, ` ```shell ` 等）
- 必须标注 JDK/框架版本（如：`// JDK 17 + Spring Boot 3.2`）
- 核心逻辑行必须有行内注释
- 代码示例必须是**完整可运行**的最小化示例，避免残缺片段

### 4.2 代码示例原则
```
✅ 好的示例：
- 展示真实业务场景（如：用线程池处理订单并发）
- 包含异常处理
- 体现最佳实践

❌ 差的示例：
- Hello World 级别的无意义示例
- 省略了关键的异常处理
- 用 System.out 代替日志框架
```

### 4.3 代码引用规则
- 引用开源框架源码时，必须标注：项目名 + 版本 + GitHub 文件链接
- 示例代码超过 50 行建议提取到 GitHub Gist 并附链接

## 五、配图规范

### 5.1 图表要求
- **架构图**：涉及组件交互的文章必须有架构图（推荐 draw.io）
- **流程图**：涉及流程/算法的必须有流程图
- **时序图**：涉及多组件交互（如 RPC 调用、消息流转）必须有时序图
- **对比表格**：涉及方案选型的必须有对比表格，不允许纯文字描述选型结论

### 5.2 图片质量标准
- 分辨率：宽度不低于 1200px
- 格式：优先 SVG（矢量清晰），其次 WebP/PNG
- 必须有图注（图 1：xxx 架构图）
- 禁止截图模糊、水印遮挡、配色混乱

### 5.3 禁止行为
- ❌ 直接使用他人博客截图（侵权风险）
- ❌ 配图与正文内容不匹配
- ❌ 没有图注说明

## 六、表达规范

### 6.1 语言风格
- **简洁优先**：能用一句话说清楚的不用三句话；能用代码演示的不用大段文字
- **主动语态**：「系统会处理请求」→「系统处理请求」
- **口语化适度**：技术内容为主，可适当加入个人见解，但避免过度口语化
- **中英文混排规范**：中英文之间加空格（如：`Kafka 的 Producer`，不写成 `Kafka的Producer`）

### 6.2 术语规范
- 首次出现的技术术语必须给出中文解释或括号注释
- 缩写首次出现时必须写全称（如：`JMM（Java Memory Model，Java 内存模型）`）
- 同一篇文章内，同一术语的中英文表达保持统一，不混用

### 6.3 禁止表达
- ❌ "众所周知"、"显然"、"不言而喻"（不应假设读者已知）
- ❌ "简单来说就是..."（后面却依然很复杂）
- ❌ 大量使用感叹号（技术文章应保持克制）
- ❌ 未经验证的技术结论（必须有来源或实验支撑）

## 七、原创与引用规范

### 7.1 原创标准
- 文章核心观点、架构图、示例代码必须是原创
- 允许引用官方文档、RFC、论文，但必须注明来源
- 翻译类文章必须在开头注明原文链接及作者

### 7.2 引用格式
```markdown
> 参考资料：
> 1. [Kafka Documentation - Producer Configs](https://kafka.apache.org/documentation/)
> 2. 《深入理解 Java 虚拟机》第3版 - 周志明，第12章
> 3. [JEP 425: Virtual Threads](https://openjdk.org/jeps/425)
```

### 7.3 禁止行为
- ❌ 整段复制他人博客内容（即使注明来源）
- ❌ 引用过时版本的官方文档（需注明适用版本）
- ❌ 引用无法溯源的二手资料

## 九、系列文章专项规范

### 9.1 系列一致性要求
- 系列首篇必须有**全系列导读**（列出所有计划篇目及当前进度）
- 系列每篇文章头部必须有**系列导航**（上一篇 / 下一篇）
- 系列内的术语定义必须保持一致（不能第1篇叫"消费者组"，第3篇叫"Consumer Group"）

### 9.2 系列导航块规范

**前缀命名约定**：每个系列使用 2~3 个大写字母缩写作为前缀，后跟两位序号：

| 系列 | 前缀 | 示例 |
|------|------|------|
| Kafka 原理与生产实战 | K | K-01, K-02 |
| Spring Boot 原理与实战 | SB | SB-01, SB-02 |
| Spring Cloud 微服务实战 | SC | SC-01, SC-02 |
| MySQL 原理与调优 | DB | DB-01, DB-02 |

**编号稳定性**：编号一旦随文章发布，**永久固定，不可重排**（同 RFC / JEP 编号语义）。系列中间需要插入新文章时，使用后缀字母（如 K-04a），不重排已有编号。

**格式要求**：
- **文章 H1 标题必须以系列编号开头**，格式为 `# K-XX 标题`（如 `# K-01 Kafka 核心概念与快速上手`）
- **归档页 `posts/README.md` 中该文章的链接文字必须与 H1 标题保持一致**，即同样包含系列编号
- 每篇文章正文开头（标题之后）必须有完整系列导航块，列出全部篇目
- 当前文章用 `👉 **K-XX 标题（本文）**` 标识，其余篇目全部使用普通链接
- 所有篇目均已发布时，不加任何状态前缀（禁用 `✅`、`⏳` 等 emoji）
- 导航块之后空一行，紧跟深度等级元数据行：`**深度等级**：⭐⭐ 进阶｜**阅读时长**：约 X 分钟｜**分类**：XX`

```markdown
> 📚 **本文属于「Kafka 原理与生产实战」系列**
> - [K-01 Kafka 核心概念与快速上手](2026-05-24-kafka-quickstart.md)
> - 👉 **K-02 Kafka 整体架构深度解析（本文）**
> - [K-03 Producer 原理与最佳实践](2026-05-24-kafka-producer.md)
> - [K-04 Consumer 原理与 Rebalance 治理](2026-05-24-kafka-consumer-rebalance.md)

**深度等级**：⭐⭐ 进阶｜**阅读时长**：约 20 分钟｜**分类**：中间件
```

### 9.3 系列收尾规范
- 每个系列完结时必须发布一篇**系列总结文章**，内容包含：
  - 全系列知识体系导图
  - 核心知识点 Checklist
  - 推荐学习资源（书籍 + 视频 + 工具）
  - 读者常见问题解答（来自评论区）

## 十、持续迭代规范

### 10.1 文章维护周期
- **发布后 1 个月内**：修正错别字、代码 Bug、读者反馈的问题
- **发布后 6 个月**：评估技术内容是否过时，必要时追加「更新说明」段落
- **发布后 1 年以上**：若技术已迭代（如 JDK 版本升级），需在文首标注⚠️过时风险

### 10.2 更新声明格式
```markdown
> ⚠️ **更新说明（2027-03-01）**：
> 本文基于 Kafka 3.x 编写，Kafka 4.0 移除了 ZooKeeper 依赖，
> KRaft 模式相关内容请参考新文章：[Kafka 4.0 KRaft 模式实战](./kafka-kraft.md)
```

### 10.3 质量复盘
- 每季度末对过去 3 个月发布的文章做一次质量回顾
- 记录：阅读量高/低的文章，分析原因，指导下一季度选题
